# Статус реализации Metro Dushanbe

Дата актуализации: 17 июля 2026 года.

## Итог

Публичный портал, backend и админ-панель готовы как локально запускаемый MVP.
Полный приёмочный контур поднимается через `infra/docker-compose.full.yml` и сохраняет
данные в именованных томах.

«Готовый MVP» здесь означает завершённые пользовательские и операторские сценарии на
демонстрационных данных. Это не означает production-ввод реального метро без официальных
данных, внешних доступов, сертификации и эксплуатационного контура.

## Что имитируется и обязано быть промаркировано

Ни один из этих контуров не является рабочим — каждый помечен как демонстрационный
и в коде, и в интерфейсе. Снимать маркировку до закрытия внешних блокеров нельзя:
показать пассажиру «билет куплен» или оператору «письмо доставлено» там, где ничего
не произошло, хуже, чем не иметь функции вовсе.

- **Оплата.** `DemoPaymentGateway` детерминированно имитирует успех/отказ. Карточные
  данные не принимаются и не хранятся вообще — приём PAN/CVV без сертификации PCI DSS
  недопустим даже в demo.
- **Каналы push/email/SMS.** Реальный провайдер есть только у `in_app`
  (см. `NotificationChannel.external()`); остальные помечаются `simulated`.
- **Получатели рассылок.** Явный demo-список: контакт-центра и правил хранения ПДн нет.
- **Телеметрия поездов.** Контур приёма готов, реального GPS-источника нет.
- **Вид билета** выводится эвристикой из срока действия тарифа
  (`TicketKind.PASS_THRESHOLD_MINUTES`) — у `fare_product` нет колонки типа продукта.
  Значение фиксируется на билете при покупке, поэтому пересмотр правила не переписывает
  уже выпущенные билеты.

## Безопасность локального MVP

- admin UI защищён HttpOnly cookie с HMAC-подписью и server-side проверкой;
- admin API защищён `X-Admin-Key`, который не попадает в browser bundle; роли операторов
  проверяются в `AdminKeyAuthFilter` и зеркалятся в `admin-actions.ts`;
- одноразовые секреты (tracking token обращения, токен билета, секрет вебхука) выдаются
  один раз, в БД хранится только SHA-256 hash, сравнение — constant-time;
- операции admin-контура создают audit events;
- production-секреты не зашиты: compose содержит только явно обозначенные dev defaults.

Локальный пароль `admin / metro2026-dev-only` предназначен только для разработки.

**Известное ограничение подписи вебхуков.** HMAC считается на `secret_hash` как на
производном ключе (`WebhookSignature`). Это исключает утечку самого секрета через
GET-ответы, логи и дампы, но НЕ защищает от компрометации БД: получив хеш, атакующий
подпишет им что угодно. Боевое решение — хранение ключа в KMS/vault; до закрытия этого
внешнего блокера схема остаётся осознанным компромиссом.

### Чего в этом прогоне НЕ было

**Интеграционные тесты на Testcontainers не запускались** — все 12 классов
`*ApiIntegrationTest` (проверяют миграции и контракты на реальном PostgreSQL/PostGIS).
Причина внешняя: на машине прогона движок Docker не поднимается — процесс `dockerd`
в WSL-дистрибутиве `docker-desktop` не стартует, API отдаёт 500 на любой запрос.
Перезапуск Docker Desktop и `wsl --shutdown` не помогли; сброс к заводским настройкам
не выполнялся, чтобы не уничтожить именованные тома приёмочного контура.

Слой не проверен — не «проверен и работает». Прогнать до подписания:

```
cd backend && ./mvnw -B test -Dtest='*IntegrationTest'
```

Аналогично не выполнялся визуальный осмотр авторизованных экранов консоли: сессия
валидируется через backend, которому нужен PostgreSQL, то есть Docker.

## Известный технический долг

- PMD сообщает архитектурные предупреждения старых классов routing/network (сложность,
  coupling, Law of Demeter); настроенная сборка считает их неблокирующими;
- CPD сообщает одну небольшую дубликацию между alert-сервисами;
- demo seed-данные намеренно остаются в репозитории для автономной демонстрации;
- локальный AI briefing не является подключением production LLM provider;
- **GTFS одноязычен**: недостающие языки заполняются строкой языка фида и порождают
  `severity=warning` в отчёте импорта — это рабочий список «что перевести», а не сбой.
  Долг закрывается переводом либо поддержкой `translations.txt`;
- **срок действия тарифа из GTFS Fares v2 не импортируется**: в формате такого поля нет
  (`timeframes.txt` — окна применимости по времени суток, `fare_transfer_rules.duration_limit` —
  окно пересадки; ни то, ни другое не является сроком годности билета). Импортированный
  продукт получает `validity_minutes = null` и предупреждение «нужно проставить срок»;
  при обновлении уже заданное оператором значение сохраняется. Выводить срок из соседних
  полей значило бы выдумать цену и срок билета;
- **носитель (`fare_media.txt`) не импортируется** — в модели нет поля носителя, добавлять
  его под формат не стали. Повтор `fare_product_id` (в GTFS легален: ключ — тройка
  id + категория + носитель) даёт ошибку импорта с номером строки, а не тихую перезапись цены;
- новый продукт из чужого фида создаётся **неактивным** — цена не должна попасть на
  публичный сайт без проверки оператором;
- `FaresGtfsImportParser` не реализует `NetworkImportParser` (другой тип результата) и не
  входит в карту форматов `ImportService` — третий вид импорта потребует общей абстракции;
- **рекомендация LLM в AI-briefing одинакова во всех трёх языках**: ответ модели рождается
  в рантайме, и источника перевода у него нет. Честное решение — передавать язык оператора
  в `briefing()` и просить модель отвечать на нём;
- индекс `ix_notification_message_status_created` не покрывает тай-брейк по `code`
  (`createdAt DESC, code ASC`) — на нынешних объёмах несущественно;
- список «мои билеты» запрашивает статус каждого билета отдельным `GET /v1/tickets/{code}` —
  на десятках билетов заметно; при реальных объёмах понадобится батч-эндпоинт;
- QR-код не рендерится: TKT-04 требует «QR/штрихкод **или** токенизированный билет», и
  токен это требование закрывает. Свой энкодер писать не стали — в контуре без сканеров и
  турникетов его нечем проверить, а битая картинка хуже честного кода текстом.

## Внешние блокеры production

Следующие пункты нельзя корректно «доделать заглушкой» без решений владельца системы:

1. утверждённые трассы, станции, расписания и источник мастер-данных;
2. утверждённые тарифы, льготы, AFC/эквайринг и платёжная сертификация;
3. production OAuth2/OIDC/Keycloak realm, роли и интеграция с гос-ID; машинный контур
   телеметрии сейчас закрыт тем же `X-Admin-Key` и обязан перейти на OAuth2 client
   credentials;
4. realtime feeds поездов, диспетчеризация и операционные SLA;
5. контакт-центр, правила хранения персональных данных и вложения к обращениям;
6. домены, TLS, secrets manager (в т.ч. KMS для ключей подписи вебхуков),
   monitoring/alerting, backups и disaster recovery;
7. Flutter-приложение, store accounts и отдельная мобильная приёмка.

До получения этих входов платформа должна оставаться маркированным demo/local MVP.
